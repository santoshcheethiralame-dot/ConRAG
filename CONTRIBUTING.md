# Contributing to ConRAG

Thank you for your interest in improving ConRAG. This guide covers how to set up, what a change must pass, and the conventions that keep the database, the code and the documentation consistent.

By participating you agree to the [Code of Conduct](CODE_OF_CONDUCT.md). To report a security vulnerability, do **not** open an issue: follow [SECURITY.md](SECURITY.md).

## Ways to contribute

- **Report a bug** or **propose a feature** through the [issue templates](.github/ISSUE_TEMPLATE). For anything larger than a small fix, please open an issue first so the approach can be agreed before you invest time.
- **Improve the evaluation.** The [roadmap](docs/ROADMAP.md) lists what is most valuable; labelled claim pairs and questions from real-world sources are especially welcome.
- **Improve the documentation.** Corrections and clarifications are always in scope.

## Development setup

You need Node.js 20 or newer. Docker is optional.

```bash
git clone https://github.com/santoshcheethiralame-dot/ConRAG.git
cd ConRAG
npm install
cp .env.example .env     # set SESSION_SECRET and SEED_PASSWORD
npx next typegen         # once, so `npm run typecheck` can see the route types
```

`npm test` needs no database server, network or API key: it starts an in-memory PostgreSQL with pgvector, applies the migrations and runs every suite. To run the application, follow the [quick start](README.md#quick-start).

## Before you open a pull request

Run all of these. CI runs the same ones.

```bash
npm run lint
npm run typecheck
npm test
EMBEDDING_PROVIDER=hash npm run eval -- --check --no-write
```

A change should also:

- **Add or update tests** for the behaviour it changes. Put pure logic in `tests/unit.test.ts`, database rules in `tests/db.test.ts`, and ingest/ask behaviour in a pipeline-style file (see `tests/ingest-candidates.test.ts`). A test that cleans up after itself with `resetData()` must do so, because suites share one database.
- **Keep the documentation true.** If you change behaviour, update the page that describes it (see [Documentation](#documentation-and-generated-files)).
- **Stay focused.** One logical change per pull request, with a description of what changed and why.

### Database changes

- Add a new numbered file in `db/migrations/` (for example `006_<what>.sql`). **Never edit a migration that has been applied**; migrations run once each, in name order, each in its own transaction.
- Enforce integrity in the database (CHECK, UNIQUE, foreign keys, triggers), not only in application code.
- Prove each rule by trying to break it in `tests/db.test.ts`. The convention is to assert the **SQLSTATE**, so the test shows the database refused, not the application.
- If the change adds a column that older rows will lack, provide a backfill (see `scripts/backfill.ts`).
- Use parameterised SQL only. Never build a statement by string concatenation of user input.

### Changing the judge, scoring or retrieval

These affect measured quality, so they need numbers, not just tests.

1. Run `npm run eval` before and after and compare `docs/EVALUATION.md`. With the default local embeddings the first run downloads the model.
2. The CI gate (`eval/thresholds.json`) fails when a metric drops below its floor. Raise a floor when quality improves; lower one only deliberately, and say why in the pull request.
3. Add a regression case to `tests/unit.test.ts` for every failure you fix.
4. Be explicit about the trade-off. Rules that call more pairs contradictory raise recall and risk precision.

## Documentation and generated files

| File | How it is produced |
|---|---|
| `docs/DATA-DICTIONARY.md`, `docs/QUERIES.md` | Generated from the live database by `npm run docs`. Do not edit by hand. |
| `docs/EVALUATION.md`, `eval/results.json` | Generated by `npm run eval`. Do not edit by hand. |
| `docs/test-output.txt` | `npm test -- --report`. |
| `docs/screenshots/`, `docs/e2e-output.txt` | `npm run test:e2e`. |
| `docs/er-diagram.png` | `npm run docs:er`, from the Mermaid source in `docs/er-diagram.md`. |

Everything else is hand-written. Keep it precise and honest: state limits next to claims, and prefer a reproducible command to an adjective.

## Code style

- TypeScript, strict. ESLint (`next/core-web-vitals`) and `tsc --noEmit` must be clean.
- Prefer small pure functions that can be unit-tested without a database, as `judge-offline.ts`, `score.ts` and `groupEvidence` do.
- Comments explain *why*, not what. Keep the existing tone: short, factual.
- Do not commit secrets. `.env` is git-ignored; `.env.example` must contain no values.

## Commits and pull requests

- Write the commit subject in the imperative mood, under about 72 characters ("Fix duplicate rule for mirrored documents"). Add a body when the reason is not obvious.
- Fill in the [pull request template](.github/pull_request_template.md).
- Keep the branch up to date with `main` and make sure CI is green before asking for review.
